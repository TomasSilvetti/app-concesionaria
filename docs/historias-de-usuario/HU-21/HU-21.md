# HU-21: Tutorial guiado para usuario demo

**Como** usuario demo,
**quiero** ver un tutorial guiado que recorra los módulos de la aplicación automáticamente al iniciar sesión,
**para** entender el funcionamiento de la app sin necesidad de asistencia.

## Descripción

Existe un usuario demo identificado por el email `demo@concesionaria.com`, asociado a una empresa ficticia llamada "demo" con su propio `clientID`. Al iniciar sesión con este usuario, la aplicación lanza automáticamente un tutorial guiado (implementado con Driver.js) que recorre los módulos principales: Operaciones, Finanzas, Cobranzas, Stock y Pendientes.

Antes de iniciar el tutorial, el sistema toma un snapshot de todos los IDs de registros asociados al `clientID` demo. Al finalizar el tutorial, compara el estado actual con ese snapshot y elimina cualquier registro nuevo generado durante la sesión, dejando los datos base intactos para la próxima ejecución del tutorial.

El tutorial no puede omitirse y se ejecuta en cada login del usuario demo.

## Criterios de aceptación

- [ ] El sistema detecta que el usuario autenticado tiene email `demo@concesionaria.com` y lanza el tutorial automáticamente.
- [ ] El tutorial no se muestra para usuarios con otro email o sin email.
- [ ] Antes de iniciar el tutorial se toma un snapshot de los IDs de registros del `clientID` demo (operaciones, vehículos, y cualquier otra entidad relevante).
- [ ] El tutorial no puede ser omitido ni cerrado antes de completarse.
- [ ] El tutorial recorre los módulos en orden: Operaciones → Finanzas → Cobranzas → Stock → Pendientes.
- [ ] Al finalizar el tutorial, el sistema compara el estado actual con el snapshot y elimina los registros nuevos del `clientID` demo.
- [ ] Los datos base (presentes en el snapshot inicial) nunca son eliminados por el proceso de reset.
- [ ] El reset afecta únicamente al `clientID` demo, sin tocar datos de otros clientes.
- [ ] En el próximo login, el tutorial vuelve a ejecutarse desde el inicio con los datos base intactos.

## Flujos

### Flujo principal (escenario de éxito)

1. El usuario ingresa con `demo@concesionaria.com` y su contraseña.
2. El sistema autentica al usuario y detecta el email demo.
3. Se toma el snapshot de IDs del `clientID` demo.
4. Se inicializa Driver.js y comienza el tutorial por el módulo Operaciones.
5. El tutorial avanza por cada módulo según los pasos definidos en cada subhistoria (HU-21-1 a HU-21-5).
6. Al llegar al último paso del último módulo, Driver.js dispara el evento de finalización.
7. El sistema compara el estado actual del `clientID` demo con el snapshot.
8. Se eliminan los registros generados durante la sesión que no estaban en el snapshot.
9. El usuario queda en la pantalla del último módulo con los datos base restaurados.

### Flujo alternativo — El usuario crea registros durante el tutorial

1. Durante el tutorial, el usuario demo crea una operación, vehículo u otro registro.
2. El registro se guarda normalmente en la BD bajo el `clientID` demo.
3. Su ID no estaba en el snapshot inicial.
4. Al finalizar el tutorial, el sistema detecta el ID nuevo y lo elimina.
5. Los datos base no son afectados.

### Flujo alternativo — Login con usuario no demo

1. Un usuario se autentica con un email distinto a `demo@concesionaria.com` (o sin email).
2. El sistema no toma snapshot ni lanza tutorial.
3. La sesión continúa normalmente.

## Notas técnicas

⚠️ **Base de datos:** Esta historia requiere que exista un usuario con email `demo@concesionaria.com` y una empresa "demo" con `clientID` propio en la BD. Los datos base deben ser cargados manualmente por el desarrollador previo al primer uso. El snapshot se construye consultando todas las entidades vinculadas a ese `clientID` (operaciones, vehículos, etc.) al momento del login.

⚠️ **Driver.js:** Instalar como dependencia del proyecto. La configuración del tour se divide en subhistorias HU-21-1 a HU-21-5, una por módulo.

⚠️ **Reset:** La lógica de comparación snapshot vs. estado actual y la eliminación de registros debe ejecutarse del lado del servidor para evitar manipulación desde el cliente. Se recomienda un endpoint interno `/api/demo/cleanup` llamado al completar el tour.
